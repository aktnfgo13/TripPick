# Phase 3.5 검증 기록

기준은 main의 f70b837이다. 기존 여행이 남아 있는 로컬 SQLite와 객체 디렉터리를 사용했다. 통합 검사는 UUID로 새 여행을 생성하고 복원 검사는 방금 확정한 여행을 다시 사용했다. API·DB 스키마와 외부 SDK 버전은 유지했다.

## 중단 재현과 원인

- **재부팅 후 QR 닫기.** 기준 APK를 공식 AVD에서 재부팅한 뒤 여행 생성·참여 QR과 소유권 QR 닫기에 성공했다. 이전 실행에서는 QR을 해독한 뒤 지도 화면이 나타났다. 당시 버튼 이벤트 기록이 없어 특정 오동작 원인을 단정할 수 없다. 화면의 QR 표시와 닫은 뒤 갤러리를 각각 확인하도록 회귀 검사를 추가했다.
- **강제 종료 후 사진 목록.** 기준 APK에서 같은 사용자의 좋아요가 남은 상세 화면을 복원해 ‘목록’을 누른 뒤 다음 단일 접근성 조회가 빈 트리를 반환하는 상황을 재현했다. 추가 진단 중 주행 화면이 포커스를 가진 상태에서 Android 기본 디스플레이의 접근성 창 목록에 TripPick이 없는 경우도 확인했다. 기존 검사에는 디스플레이·패키지 검증이 없고 같은 XML 경로를 반복 사용했다. 현재 검사는 고유 덤프 파일, 대상 디스플레이와 앱 창, 셀렉터 기반 제한 시간, 런처 기동 후 화면 준비 조건을 사용한다. 실제 버튼을 누르고 결과를 확인하며 복원 화면을 건너뛰지 않는다.
- **앱에서 확인한 결함.** 서버 목록에 없는 사진을 고르면 화면은 목록으로 떨어졌지만 로컬 선택 ID는 남았다. 지도에서도 제외된 장소를 가리키는 선택이 남았다. 여행 조회가 401/404인 경우 현재 여행을 계속 조회했다. 이제 성공한 서버 스냅샷을 기준으로 사진·지도 경로를 정리한다. 401/404면 현재 로컬 연결을 풀고 여행 선택으로 복귀한다. 일시적 I/O 오류에는 기존 선택을 유지하고 한국어 새로고침 안내를 표시한다. 여행 생성의 저장 목록을 스크롤할 수 있게 하고 갱신 표시가 버튼 위치를 밀지 않도록 했다.

## 빌드와 통합 시험

- 공식 Pleos Connect Emulator 2.1.0 arm64, API 34, Vehicle 2.3.2, NaviHelper 3.0.5. 최종 디버그 기본·SDK APK 각각 빌드와 JUnit 4건 통과. 백엔드 9건, 모바일 웹 2건과 TypeScript 검사·배포 빌드 통과.
- 최종 SDK APK에서 신규 여행 → QR 해독 → 독립 Chrome 컨텍스트 4개 참여 → 서로 다른 PNG 업로드 → 모바일·차량의 동일 계정 좋아요 취소·재등록 → 앱 강제 종료·상세 및 목록 복원 → 차량 관리자 앨범 확정 → 네 브라우저 다운로드를 확인했다. 네 다운로드가 모두 선택한 업로더의 원래 바이트와 같았다. 추가 실행에서 차량 시스템 창에 포커스가 넘어가 초기 화면 검사가 중단된 적이 있어 앱이 실제로 보이는 조건을 명시했다.
- 로컬 측정에서 사진 메타데이터 500건은 13페이지, 71,785바이트, 21.3ms였다. 이미지 500개 전체 업로드·프레임률 실측치는 아니다. 초기 및 revision 변경 시 클라이언트가 전체 메타데이터 페이지를 조회한다. 썸네일은 웹 lazy 이미지와 차량 LazyVerticalGrid가 요청한다. 백엔드 회귀는 중복 요청·동시 투표·앨범 revision 충돌·세션 만료·WebSocket 재접속을 포함한다.
- 모바일은 로컬 HTTPS의 Chrome 컨텍스트로 검사했다. 실차·실물 스마트폰은 실행하지 않았다. 이번 주행 검사는 사용자 조작 제한을 대상으로 하며 실제 내비 목적지 변경·도착 콜백의 검증 범위는 Phase 3 보고서와 같다.

## 지도와 데이터

차량과 모바일에서 수동 등록한 충남 장소, 연결 사진, 여행일지를 열고 전국으로 복귀했다. 국내 공개 지점을 사용한 별도 Chrome 검사는 17개 지역의 실제 SVG 경로와 시·도 코드, 방문 지역 강조, 지역 상세 도형 1개, 같은 지역의 핀 1개와 좌표·선택을 확인했다. 이 지점들은 시험 메모리에서만 사용했다. GPS 경계 정밀도에는 한계가 있다. 광주시청 인근 점 하나가 전남으로 분류됐으며 2021년 이후의 군위군 편입도 미반영이다. [지도 원자료·라이선스·코드 유지 원칙](../assets/maps/SOURCE.md)

## 구조 검토

- 차량의 세션 저장, HTTP, 지도 도형, 방문 조회, NaviHelper 소스 세트는 분리돼 있다. TravelModel은 여행·투표·갤러리를 함께 조율하지만 이번 결함은 서버 응답 적용 경계에서 수정할 수 있었다. QR은 재발급 가능한 임시 화면이다. 선정 중인 미확정 편집은 메모리에 둔다.
- 백엔드는 여행 권한을 요청마다 검사한다. 여행일지·앨범 수정에서 BEGIN IMMEDIATE, 역할·소유자 및 revision을 확인하는 경로를 대조했다. 사진 업로드 서비스는 ObjectStore 프로토콜을 사용하고 중간 실패 시 객체를 정리한다. R2 구현과 원격 스토리지 시험은 별도 작업이다.
- 모바일의 업로드 큐, 공통 HTTP, 여행일지 렌더러는 분리돼 있다. TripRoom에는 목록·투표·앨범 상태가 함께 있으며 대량 사진에서 메타데이터 전체 재조회가 남는다. 중복 WS·HTTP 갱신을 제한하는 기존 설계를 유지했다.

## 재현

1. README의 로컬 서버와 두 APK 빌드 절차를 사용한다. SDK APK는 10.0.2.2:18081, QR은 trippick.test:19444로 설정한다. 전용 AVD에 최종 APK를 설치하고 Android MAIN/LAUNCHER로 시작한다.
2. TRIPPICK_TEST_LOOPBACK=1과 TRIPPICK_TEST_JOURNAL=1로 tests/integration/pleos_album.py를 실행한다. 전용 DB 외 기존 데이터는 지우지 않는다.
3. 공식 Host Display Bridge에서 DISPLAY2를 각 방향으로 생성한다. 재생성할 때 Android 논리 ID를 다시 조회하고 해당 디스플레이에 앱을 실행한다. TRIPPICK_TEST_DISPLAY와 TRIPPICK_TEST_SCREENSHOTS를 지정해 pleos_layout.py를 실행한다.
4. 기본 화면으로 돌아와 pleos_restore.py를 실행한다. 공식 Virtual Console은 포트 8088 포워딩과 브라우저 heartbeat가 필요하다. pleos_expiry.py에는 전용 TRIPPICK_TEST_DB 경로를 지정한다. TRIPPICK_TEST_NETWORK=1 및 TRIPPICK_TEST_API_PID를 지정하면 명시한 127.0.0.1:18081 전용 uvicorn 프로세스의 명령행과 리스닝 주소를 검증한 뒤 잠시 정지·재개한다. 별도 HTTPS 서버에서 그동안 참가자를 추가한다. map_areas.py에는 로컬 TRIPPICK_TEST_ORIGIN을 지정한다.

## 이전 여행·오프라인·주행 시험 결과

확정 여행에서 차량 앱 강제 종료와 AVD 재부팅 후 같은 여행 ID, 상세 사진, 본인의 좋아요를 확인했다. 참여 QR을 다시 열어 판독하고 닫은 뒤 공유 앨범으로 이동했다. Virtual Console에서 Drive와 속도를 적용하자 조작 제한 안내가 표시되고 사진 버튼이 사라졌다. 속도 0과 Park 복귀 뒤 같은 사진 상세, 좋아요, 공유 앨범을 다시 확인했다.

전용 AVD의 글로벌 HTTP 프록시만 변경한 초기 시도에서는 서버 연결 장애가 발생하지 않았다. 다음 실행은 테스트용 HTTP 서버만 일시 정지해 타임아웃과 한국어 안내를 확인했다. 독립 HTTPS 서버에서 그동안 참가자를 추가한 뒤 HTTP 서버를 재개하고 차량에서 새로고침하자 같은 여행에 새 참가자가 나타났다. 해당 시험 여행의 차량 세션만 만료시키고 여행 선택 화면 복귀 및 서버 여행 행 보존을 확인했다.

최종 APK SHA-256은 기본판 86015bcf98177edc78ab42f379a5c772a6413c5d405aa8eac596d7266a5e2009, SDK판 895e11914f6969b97948bce2731cfe6516baf0dcc37a6699d179f5e2664918ab이며 두 파일 모두 apksigner verify를 통과했다.

## 폼 팩터와 주행 제한의 적용 범위

공식 Host Display Bridge로 DISPLAY2를 1440×2560 및 2560×1440, 160 dpi로 각각 생성했다. 기존 여행 창을 대상 디스플레이에 띄운 뒤 홈, 생성 폼, 참여 QR 판독·닫기, 사진 목록, 상세와 좋아요 버튼, 공유 앨범, 전국·지역 지도, 장소 상세·여행일지, 장소 앨범을 두 방향 모두 조작했다. 각 상태를 실제 캡처했다. 네 사용자 간 좋아요 변경은 기본 화면의 통합 시험에서 별도로 확인했다. [세로 캡처](phase3_5/portrait.jpg) · [가로 캡처](phase3_5/landscape.jpg)

보조 화면에 옮긴 기존 창은 원래 작업 크기를 사용해 검은 여백이 생겼다. 세로에서는 오른쪽 가장자리의 일부 내용이 잘린다. 전체 해상도에 맞는 독립 작업으로 다시 열면 TripPick 창이 실제 1440×2560으로 잡혔으나, Park·0 km/h에서도 앱은 주행 제한 안내를 유지했다. car_service가 표시한 UX 제한 대상에는 display 0만 있었다. 이 조건에서 DISPLAY2 독립 작업의 전체 화면 시각 품질은 검증 보류다. [공식 폼 팩터 절차](https://document.pleos.ai/docs/pleos-only/app-test-guide/form-factor-test-guide)

기본 디스플레이의 Pleos 분할 화면에서는 기존 앨범 전체 흐름과 터치를 검증했다. 주행 제한 서비스가 적용되는 기본 디스플레이에서 1440×2560 세로 및 2560×1440 가로 전체 화면으로 같은 10개 화면 상태를 다시 캡처했다. 양쪽 모두 장소 핀, 여행일지, 사진, 버튼이 겹치지 않았으며 QR 판독과 터치 순회를 통과했다. 1280×720에서는 저장된 여행 목록을 양방향으로 스크롤해 항목 위치가 바뀌고 기존 여행으로 돌아오는 것을 확인했다. [기본 화면 세로](phase3_5/primary-portrait.jpg) · [기본 화면 가로](phase3_5/primary-landscape.jpg) QR 캡처는 판독 후 코드를 가렸다. 단색 썸네일은 네 업로더를 구별하도록 만든 서로 다른 크기의 PNG다.

## 다음 우선순위

1. 공식 에뮬레이터에서 독립 DISPLAY2에 주행 제한 정보가 제공되는 조건을 확인하고, 세로 오른쪽 가장자리와 전체 화면 레이아웃을 다시 검사한다.

3. 실제 스마트폰 및 실차에서 QR, 네트워크 전환, 실제 목적지 변경·도착을 검증한다.
